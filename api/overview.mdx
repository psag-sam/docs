The Pearl CRM API lets another system read and write CRM records on behalf of an organisation. It has three parts:

- an **OAuth 2.0 server** that issues access tokens,
- a **REST API** at `/api/v1/crm` for reading and writing individual records, and for batches of up to 200 operations,
- a **Bulk API** at `/api/v1/crm/jobs` for loading large files asynchronously.

## Base URL

```text
https://api.pearlcrm.com
```

Every REST and Bulk path in these pages is relative to `https://api.pearlcrm.com/api/v1/crm`. OAuth endpoints live at the root, for example `https://api.pearlcrm.com/oauth/token`.

The live OpenAPI document is at `/api/v1/crm/openapi.json`, and an interactive explorer at `/api/v1/crm/docs`. Both are generated by the running service, so they match what is deployed.

## Before you start

<Steps>
  <Step title="The organisation needs the API Access & Integrations add-on">
    The API is sold as the **API Access & Integrations** add-on. Without it, the organisation cannot create clients and API calls are refused.
  </Step>
  <Step title="An administrator creates a client">
    In Pearl CRM, go to **Settings → Developer & API** and create a client. A server-to-server integration uses the client credentials grant and is linked to a role. An app that acts for a signed-in user uses the authorization code grant with PKCE. See [Authentication](/api/authentication).
  </Step>
  <Step title="Choose scopes">
    Give the client only the scopes it needs, for example `leads.read leads.write`. See [Scopes and permissions](/api/scopes).
  </Step>
</Steps>

## Objects

The API exposes these objects by their API name:

| API name | Read | Write |
|---|---|---|
| `leads`, `accounts`, `contacts`, `deals` | Yes | Yes |
| `activities`, `products`, `cases`, `opportunities`, `customers`, `travel_contacts` | Yes | Yes |
| `orders`, `quotations`, `invoices`, `tasks`, `trips`, `trip_packages`, `travel_orders`, `coupons` | Yes | Not yet |

Writing a read-only object returns `405 read_only_object`. Some objects depend on a module, such as the travel objects. When the organisation does not have that module, calls return `403 module_not_entitled`.

`GET /objects` lists what the token can reach, and `GET /objects/{object}/describe` returns each field with its type, whether it can be filtered, whether it is writable and whether it is required on create.

## Versioning

The version is part of the path (`/api/v1`). New objects, fields and optional parameters can appear within a version, so integrations should ignore fields they do not recognise.

## Responses

Successful responses are JSON. A single record is wrapped in `data`:

```json
{ "data": { "id": 512, "last_name": "Nguyen", "external_id": "crm-8841" } }
```

Errors always use the same envelope, described in [Errors and limits](/api/errors-and-limits):

```json
{ "error": { "code": "insufficient_scope", "message": "This token lacks the leads.write scope", "scope": "leads.write" } }
```
